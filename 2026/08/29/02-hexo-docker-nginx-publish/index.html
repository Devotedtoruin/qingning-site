Hexo 7 静态博客构建、布局修改与 Docker/Nginx 发布

#Hexo#Docker#Nginx#Git

静态站点维护分为三份：Hexo 源码保存文章、布局和配置；public/ 是可再生成产物；发布端目录只接收已生成文件。因此云端无需 Node 或 Hexo，构建问题与服务问题也可以分层处理。

如果目标已经存在或非空，先确认它的用途，不要覆盖，也不要直接 chown -R 一个用途未知的目录。产物仓库可使用公开只读地址，私有仓库则使用专用只读 Deploy Key；不要把 Token 写进远程 URL。日常更新才使用 git pull --ff-only。

首次 Docker/Nginx 托管

安全前提：不要直接把 Git 工作区根目录作为公开站点根目录。 下列传统挂载示例中的 DEPLOY_DIR 含 .git/；只读挂载只限制写入，不能防止 HTTP 读取 .git/config、对象或历史文件，远程地址也可能泄露。正式上线应使用不含 Git 元数据的独立静态目录，或先配置并验证 Nginx 对 /.git 及其所有子路径的拒绝规则（含别名/其他入口）；未完成隔离或拒绝验证，不得照搬下面默认镜像挂载方案开放公网。rsync 保留 .git 只是维护工作区，不是 HTTP 访问保护。

更新、重建与回退

修改 Markdown 或主题后，先本地预览并重新构建，再发布新产物。Nginx 始终读取同一 Bind Mount，因此仅更新静态文件时不需要重建容器；只有镜像、端口、容器参数、Nginx 配置或挂载关系变化时才需要重建。

首选的日常更新仍是上面的 git pull --ff-only。下面的 rsync --delete 只用于发布端需要从一份已经验收的静态产物目录做受控替换或回退时；这些命令在 VM/云端发布主机 上执行，不是在本地 Hexo 源码目录中执行。--delete 会删除目标中来源没有的文件，变量为空、方向写反或跨错主机都可能破坏发布目录。

先在发布主机设置来源、目标和独立备份目录。三者必须已经存在、用途明确，并且规范化后两两不相等、不互相嵌套。备份根目录由发布账号拥有且可写；不要为通过检查对未知目录递归改属主。本例由发布账号执行 rsync，以 --no-owner --no-group 避免沿用来源属主，目标中已有文件也须具有所需读写权限。

下面是一个完整子 Shell：校验或备份失败会终止整个块；dry-run 后需要输入 yes 才会继续。不要拆开执行后半段，变量只在该子 Shell 内有效。路径检查不能保证任意路径绝对安全，不能防止并发替换、所有符号链接、特殊挂载或错误的业务目录选择；须人工确认静态内容、权限、空间和目标边界，并避免同步期间其他发布任务修改这些目录。

根目录级 protect 与 exclude 规则用于保留目标 .git/；不要添加 --delete-excluded。异常时不要继续同步。回退使用同一个完整块，但将 SOURCE_DIR 填为本次打印并核验过的 BACKUP_DIR，将 BACKUP_ROOT 设为与此来源、目标均不嵌套的另一个已准备备份目录；重新检查路径、备份当前状态和审阅 dry-run 后再确认。不能将原备份根目录直接沿用，因为它包含回退来源。回退保留当前 .git/，不会回退 Git 历史；恢复后另行执行 git -C "$DEPLOY_DIR" status -sb 并核对内容与版本，不要未经检查直接 pull 覆盖恢复内容。

容器启动失败先查 docker logs、nginx -t、挂载和端口，不删除运行目录或容器作为默认修复。

后续接入与验收

先完成公网 HTTP 验证，再单独处理域名、备案、DNS 和 HTTPS。上线前检查：public/包含首页、文章和 search，配置正式 canonical URL 后还应包含 Atom；发布端版本或哈希正确；容器、挂载、端口、本机 HTTP 和公网 HTTP 均正常；上一版产物可以恢复。

发布前根据实际环境填写私密部署配置，并确认仓库权限、云网络规则和容器参数。凭证不要写入源码或生成文件。
