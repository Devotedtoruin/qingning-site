Docker/Nginx 静态博客的重启恢复、日志轮转与安全重建

#Docker#Nginx#恢复#日志

前两篇分别完成服务器初始化和静态站点首次发布。站点运行后，还需要验证主机重启是否能恢复服务、容器日志是否有边界，以及如何在不丢失回退路径的前提下修改容器参数。本文面向由 Docker 内 Nginx 通过只读 Bind Mount 提供静态文件的站点。

本文使用通用变量，命令应在服务器上以具有 Docker 管理权限的账号执行。变更容器前保留可用的管理入口，并确认当前站点存在可用基线；不要在没有证据时直接重启、删除或清理资源。

适用范围、风险与变量

示例假定容器使用固定镜像、端口映射、只读 Bind Mount 和 unless-stopped。修改日志配置会创建新容器，因此先记录原参数；在验证完成前，旧容器只作为临时回退点，不是新的运行实例。

1. 变更前建立基线

先记录请求目标、检查时间和最近变更，并收集能够决定下一步的最小信息：

systemctl、容器状态、挂载、监听和 HTTP 检查分别回答不同问题。服务器监听只说明本机端口接受连接；本机 HTTP 只证明主机到应用的链路；公网 HTTP 才覆盖外部网络路径。它们不能相互替代。

容器显示 Up 或某次请求返回 HTTP 200，也不自动证明挂载源、静态产物版本和请求目标正确。需要同时核对挂载、发布目录和实际响应。

2. 主机重启后的恢复验证

主机重启后，按固定顺序检查，避免因为一个成功结果跳过其他层：

  1. 管理入口：先确认新的 SSH 会话可连接，避免占用唯一会话做后续操作。
  2. 系统服务：确认 Docker 为 active/enabled，并查看失败单元数。
  3. 容器与重启策略：确认目标容器为 running，RestartCount 合理，策略为预期值。
  4. 挂载与监听：确认发布目录仍以只读方式挂载，宿主机端口仍在监听。
  5. 本机和公网请求：分别核对 HTTP 状态与响应大小；必要时再比较响应体或版本标识。
  6. 日志：查看重启时段的容器日志，确认应用完成正常启动。

Nginx 收到 SIGQUIT、worker 以 code 0 退出，随后 entrypoint 和 Nginx 再次启动，是 graceful shutdown 后正常恢复的一组证据。必须结合后续启动记录和 HTTP 验证判断，不能孤立当作异常日志。

3. 检查 json-file 是否真正轮转

json-file 表示 Docker 收集容器的 stdout/stderr 并写入 JSON 日志；它本身不表示已经限制日志大小。应同时检查容器级配置和 Docker 守护进程默认选项：

当容器选项和守护进程默认中的 max-size、max-file 都没有设置时，当前日志即使较小、服务也正常，仍存在长期磁盘增长风险。它不是已经发生的磁盘故障，更不能据此推断历史故障根因。

守护进程默认日志选项通常只影响之后新创建的容器；既有容器不会自动继承新默认值。因此需要按已记录参数创建新容器，再验证新容器的日志选项。

4. 安全重建与临时回退

不要用 docker system prune、模糊名称删除或未经检查的 docker rm -f 来处理单个容器。安全流程如下：

  1. 保存原镜像、端口、挂载、重启策略和日志配置。
  2. 停止旧容器并重命名，保留它作为临时回退点。
  3. 使用原镜像、端口、挂载和重启策略创建新容器，同时明确日志轮转参数。
  4. 核对新容器配置、运行状态和重启次数。
  5. 完成本机与公网 HTTP、挂载、监听和日志的分层验证。
  6. 经过稳定观察后，单独获得删除旧容器的授权。

5. 验收与交接

在删除临时回退容器前，至少确认：

  • Docker 服务 active 且 enabled，失败单元符合预期；
  • 目标容器为 running，RestartCount 为预期值，重启策略正确；
  • 发布目录为只读 Bind Mount，端口映射与监听正确；
  • json-file、max-size 和 max-file 已在新容器上核对；
  • 本机和公网 HTTP 均成功，响应状态与大小符合基线；
  • 对应时段 Nginx 日志显示正常启动和请求；
  • 旧容器仅在稳定观察结束且获得单独授权后删除。

完成这些检查后，记录变更时间、基线与验证结果。源码版本与可重建产物应由既有版本库保留；运行中的发布副本不自动构成独立备份。
