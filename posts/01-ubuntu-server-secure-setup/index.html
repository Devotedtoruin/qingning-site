Ubuntu SSH：公钥登录与端口迁移

2026年9月1日 · 学习笔记 · 约 11 分钟阅读

更新于 2026年9月5日

在 Ubuntu 24.04 上建管理账号、配置公钥登录，再按 socket/service 分支把 SSH 端口安全地换掉。

#Linux#SSH#服务器安全

本页目录

    新服务器到手，第一件事通常是用 root 和密码登进去。临时用没问题，但长期这样并不合适：root 权限太大，密码还可能被反复尝试。更稳妥的做法是建一个普通管理账号，用密钥登录，再把 SSH 入口换到一个不常用的端口。

    这件事按顺序做，风险会小很多：先建账号和密钥，再放行新端口，确认新入口能用，最后才关掉旧入口和密码登录。如果一上来就改端口，很容易把自己锁在服务器外面。

    本文以 Ubuntu Server 24.04、systemd 和 OpenSSH Server 为例。开始前请确认三件事：你有一个能用的 sudo 账号、一台带 OpenSSH 客户端的电脑，以及云控制台或虚拟机控制台。最后一项很重要，它是 SSH 断开后的退路。

    学习路线 · 01 这篇属于“从服务器到前端”的学习路线。查看完整路线 →

    第一步：建账号，配公钥

    先在客户端生成一把专用密钥。Ed25519 足够用，给私钥设置口令；如果目标文件已经存在，换一个文件名，不要覆盖旧密钥。

    私钥留在客户端，只有 .pub 公钥需要上传。私钥不要贴到聊天窗口、网页表单或服务器的 authorized_keys 里。

    接下来在服务器上创建管理账号。下面的 adduser 只对新账号执行；如果账号已经存在，直接跳过。

    adduser 会交互设置密码，这个密码也可以用于 sudo。后面禁用的是 SSH 密码认证，不是账号密码本身。id 的输出里应该能看到 sudo 组；组权限要等新登录会话才生效。

    如果当前服务器还允许密码登录，直接用 ssh-copy-id 安装公钥最省事：

    第一次连接前，通过控制台核对一次主机密钥指纹。不要为了省掉确认而关闭主机密钥检查。ssh-copy-id 提示“尝试登录”只说明公钥可能写进去了，还要用下一步单独验证。

    有些镜像默认已经禁止密码登录。这时不要为了传公钥再把密码认证打开，直接在服务器上追加公钥：

    第二步：先放行新端口，再改监听

    迁移端口的顺序只有一条：放行新端口 → 同时监听新旧端口 → 从外部验证新端口 → 移除旧端口。任何一步没确认，都不要急着做下一步。

    先处理云安全组和主机防火墙

    在云安全组或上游防火墙里放行新 TCP 端口，同时保留旧规则。然后检查主机防火墙。两层都要放行，只改一层不够。

    如果服务器启用了 UFW，先看规则，再按管理来源添加新端口：

    UFW 没启用时，不要在远程迁移中顺手执行 ufw enable。使用其他防火墙的服务器，按现有规则管理方式放行即可。

    从外部验证，再移除旧入口

    在客户端新开终端，用新端口、公钥和新账号连接：

    确认主机指纹、whoami 和 sudo -v 都正常。服务器本机能连上新端口，不代表外部安全组和路由也正确。

    新入口确认可用后，再回到对应的 socket drop-in 或 sshd 配置里删掉旧端口，按同样的方式重新应用。用 ss 确认旧监听消失，最后再收紧旧端口的网络规则。如果旧规则还被别的服务使用，不要一起删掉。

    连接失败时，可以按现象缩小范围：

    • 超时：先看安全组、主机防火墙和监听地址。
    • 连接被拒绝：先确认端口是否真的在监听。
    • Permission denied：检查用户名、公钥和认证日志。

    旧会话还在，就保留双端口配置逐项检查。已经失联，就进控制台按备份恢复：恢复原文件，撤掉本次新增但备份中不存在的配置，再按原分支应用。socket 分支需要 daemon-reload 和重启对应单元；service 分支在语法检查后重载。恢复后从外部重新连接一次，不要只在控制台看状态。

    第四步：更新系统，按需重启

    SSH 入口稳定后，再安排系统更新。不要把端口迁移、升级和重启挤在同一次操作里。

    apt update 只刷新软件索引。确认维护窗口和变更内容后，再运行 sudo apt upgrade，看完交互摘要再决定是否继续。教程里不需要用自动确认把可能的重启藏起来。

    需要重启时，先确认控制台和新 SSH 入口都能用，再安排时间。机器重新上线后，重新检查端口、普通账号公钥登录和 sudo。
