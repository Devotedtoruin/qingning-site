    Server Survival 与 Datacenter Survival：两款运维模拟游戏

    从请求路由、队列与扩容，到机房供电、散热与备用链路：借两款浏览器游戏梳理故障假设、观察指标和模拟的局限。

    #开源项目#模拟游戏

    请求失败，可能是服务间没有可用路径，也可能是承载服务的机架断了电。pshenok 的两款浏览器游戏分别把这两层问题摆到画面上：Server Survival 管服务、流量与请求处理，Datacenter Survival 管供电、散热与机架运行。

    本文是依据官方说明和固定版本源码整理的机制解读，不是本站试玩报告。下面的故障情景是待执行的观察方案，没有附会通关成绩、实测延迟或个人体验。在线入口会随项目更新，机制说明则限定在下列提交；若网页表现不同，先比较版本，而不是认定自己的操作一定有错。

    游戏 在线游玩 本文核对版本
    Server Survival 打开游戏 7804e596
    Datacenter Survival 打开游戏 3f258297

    官方 README 说明，两款均可直接在浏览器游玩，无需安装、构建或注册。Campaign 用逐关目标引出机制；自由实验入口适合一次只改变一个条件。不要把自由模式中关闭成本后的结果与生存模式直接比较。

    Server Survival：请求走到了哪里

    计算节点、数据库、缓存与队列各有不同职责。请求从入口沿有方向的连线流动，能否完成，取决于可达路径、请求类型、处理容量与服务状态。成功请求带来收入，失败或恶意流量泄漏影响声誉，节点还有持续维护费用。因此“连上了”和“处理成功了”是两个判断。

    从入口开始搭出第一条请求路径

    1. 打开官方入口，选择 Campaign，再进入首关 The First Server；需要不受关卡目标限制的实验则选择 Sandbox。
    2. 用时间控件暂停，先阅读目标和预算。工具栏按 Front Door、Compute、Data、Async、Ops 分类；选择服务后左键放置。
    3. 首关可尝试依次放置 Firewall、Load Balancer、Compute 与 Relational DB，再选 Link（C），按上游 → 下游的顺序点击两个节点，连接 Internet → Firewall → Load Balancer → Compute → Database。这是一条待观察的搭建路径，不是保证零失败的通关攻略。
    4. 回到 1 倍速，检查 READ 完成数、声誉、节点健康和失败徽标。若请求没有抵达数据库，先查方向和缺失连接；不要一开始就用 3 倍速掩盖过程。
    5. 需要重新查看画面时，右键拖动平移，滚轮缩放，R 重置相机；T 切换俯视角。手机可点按放置、双指平移与缩放，但部分视角操作只支持键盘。

    第一关并不是已经搭好的完整系统

    首关 The First Server 的主目标是完成至少 50 个 READ 请求，声誉达到至少 80%；零失败和速度目标属于奖励条件。这里有一个容易被介绍文字带偏的细节：固定版本的 src/campaign/levels.js 中，第一关 preBuilt.services 和 connections 都为空。Internet → Firewall → Load Balancer → Compute → Database 是理解和搭建的路径，不应写成开局已预置的整条链。

    该关并非只有 READ：配置还包含 WRITE 与少量 MALICIOUS。这意味着只盯着蓝色读请求，可能漏掉写入失败与防护问题。判断顺序应是：请求是否进入正确入口、连线方向是否正确、下游是否支持这种请求、实际有没有完成，再考虑是否缺容量。失败徽标有助于区分无路由、队列已满和只读节点拒绝写入，不必一看到失败就加服务器。

    缓存和只读副本改变的是负载去向

    缓存减少到数据库的读取压力；只读副本把部分 READ 从主库分流。它们不是“所有数据库问题的通用修复”。固定版本 src/sim/handlers/replica.js 明确检查副本是否连接到数据库或 NoSQL 主节点；没有主节点会失败，副本也不会接受 WRITE。

    可以在 Sandbox 先固定流量构成，再比较有无缓存或副本的两份拓扑。故障假设是：数据库压力主要来自可分流读取，而非写入或缺路由。若增加副本后主库仍忙，需要继续看 READ 是否真的走向副本、WRITE 占比是否上升，以及入口或 Compute 是否成为新瓶颈。观察完成请求数、类型构成、失败原因与各节点负载，比仅看声誉变化更接近问题本身。

    真实系统还需处理复制延迟、读后写一致性、缓存失效与热点键。游戏把这些成本压缩为较少的状态，不能从“游戏中读取成功”推导生产环境可以无条件读副本。

    队列把突发压力换成等待

    Message Queue 的价值是缓冲，不是创造处理能力。固定版本的 src/sim/handlers/sqs.js 会检查下游容量；Compute 从队列拉取任务，队列不会不加限制地把所有请求推给计算节点。这里可以理解背压：下游忙时，上游暂存，避免立刻把压力放大。

    待验证的情景是先短时突发，再恢复原流量，观察队列是否逐步排空。若恢复后仍增长，问题更像是长期到达速率超过处理速率，而不是队列太小。在真实系统中，队列长度、最老任务年龄、消费速率、重试次数和死信数量要一起看；短时间无丢弃不代表任务符合时限。

    “队列更长，所以系统更可靠”也有条件。用户请求可能已经超时，重复执行可能造成副作用，持久化与确认策略可能影响丢失风险。游戏中的暂存反馈并不能替代消息中间件的持久性或幂等性设计。

    扩容和限流要看生效时间

    官方说明中，Compute 会依据利用率扩缩容，队列驱动的计算组还会响应队列压力；新实例存在预热时间。扩容决策发生了，不等于当前一秒就多出可用容量。API Gateway 的限流则主动减少进入下游的请求，与让请求挤到失败有不同的反馈代价。

    可以提出两个分开的假设：突发太短，新增实例来不及投入；或者持续压力足够长，但瓶颈其实在数据库，增加 Compute 只让更多请求排到同一处。观察时应区分请求到达量、完成量、错误率、延迟、队列积压、预热实例和维护费用。Monitoring 节点提供实时指标和告警入口，不过游戏仪表不是生产监控系统的完整替身。

    固定版本 Campaign 共 25 关、5 章，逐步加入防御、可观测性、多区域及推理服务。这里不把某个游戏阈值当成生产建议：扩容阈值与熔断窗口必须结合业务时限、容量测试和成本重新设计。

    Datacenter Survival：机架为什么停了

    机架有电且温度允许时才能正常承载工作。供电链、冷却和成本互相牵制：增加冷却会耗电；共享冷却可以降低重复开销，却把多个机架放进同一个故障影响范围。

    先在实验场观察一条完整链路

    1. 打开官方入口，从菜单进入 The Lab。它不要求先通关，可在已有设备上观察，不必从空场地猜接线。
    2. 沿 Grid Feed → Transformer → UPS → PDU → Rack 查看连接，辨认备用发电机与冷却设备所在位置，记录未改动时的需求、供电和温度。
    3. 先只调整需求，观察机架与支路；再单独触发一次 grid outage（市电中断），看 UPS 缓冲、发电机接入和未服务功率。不要同时触发热浪与停电，否则难以区分因果。
    4. 用 T 打开热力视图，再单独试 heatwave 或 CRAC failure；检查冷却是否有电、热点在哪里、哪些机架降额。右键或中键拖动、WASD 或方向键可平移画面。
    5. 熟悉这些状态后再进 Campaign 首关 First Watt，按目标搭供电链。实验场没有目标倒计时，不代表生存模式没有预算与服务损失压力。

    以上操作入口依据固定版本官方 README；在线部署若改名或改变菜单，以实际界面为准。本文未执行这组实验。

    容量取决于整条供电链

    官方说明的典型链路是 Grid Feed → Transformer → UPS → PDU → Rack，每个环节都有功率容量。上游超载会限制下游；继续过载还可能让断路器跳闸。这比“机架数量乘额定功率”多了一层约束：总供电够用，不代表某个 PDU 支路够用。

    第一关 First Watt 聚焦把电送到负载，后续再引入热、备用电力与诊断。面对“有些机架不工作”，先沿支路看连接、设备状态与容量，再判断市电是否整体中断。不能仅因为机房总需求低于总容量，就排除局部过载。

    待验证的情景是增加同一支路的需求，保留另一支路不变，观察故障是否集中到共享上游的机架。应记录需求功率、实际供电、未服务功率、故障徽标和损失归因，而不只是当前余额。真实设施还要考虑相位、保护协调、线缆、额定条件与维护规程；游戏里的连线不是电气设计图，更不能据此操作实际设备。

    UPS 与发电机解决不同时间尺度的问题

    UPS 为切换间隙提供缓冲；备用发电机接续较长中断，但启动、接入和燃料都是条件。建了备用设备，不等于每个负载都接到了备用路径，也不等于剩余电量足够支撑切换。

    The Lab 从开始即可进入，预置含 UPS、备用发电机、机架与 CRAC 的工作链路。它可调需求、环境温度和电价，也可主动触发热浪、电压跌落、市电中断、峰值电价窗口或 CRAC 故障；没有任务目标或倒计时。适合重复触发同一种中断，比较负载所在支路、UPS 剩余缓冲和发电机接入过程。本文没有执行这组比较，因此不宣称某配置实现了零中断。

    真实冗余还要看共同故障域。两路供电若共享同一上游，设备数量增加也未必隔离风险；能在故障时切换，与能够在计划维护时持续服务，又是不同要求。游戏关卡提供理解入口，不构成 Tier 认证或可维护性审计。

    降温、PUE 和费用不是同一个目标

    游戏中的热扩散与冷却覆盖使布局有意义。T 打开热力视图，可用于观察热点；它与 Server Survival 中切换俯视角的 T 不同。假设是冷却覆盖不当时，增加远处设备不如修正覆盖位置；还应检查冷却是否有电，而不是只数冷却器。

    PUE 是设施总用电与 IT 用电之比。在相同负载与观察窗口下，比较 PUE 才有解释力。不能把“PUE 下降”单独当成任务成功：机架是否持续工作、服务量是否满足需求、温度是否允许、总费用如何，都需要一起判断。现实的计量边界、统计周期和负载结构也影响可比性。

    固定版本还包含冷水机组与 CRAH 的共享回路，以及用水和 WUE 的反馈。共享设备带来规模效率，也形成共同失效点；节电并非唯一资源目标。一次冷却故障方案应同时记录热点、降额、服务损失与费用，避免把能效数值当成可靠性的替身。

    把机制转成可检查的故障假设

    以下是建议观察的问题，不是已经完成的实验结果。

    情景 先提出的假设 要一起看的证据
    请求突然大量失败 路由或特定节点容量受限 类型、失败徽标、节点负载、完成量
    加队列后不再立即丢弃 短时积压可以被后续消费 队列是否排空、等待时间、后续失败
    新实例出现仍很慢 预热尚未完成或瓶颈在下游 可用实例、数据库负载、完成量、费用
    一部分机架失电 同支路共享上游受限 支路、实际供电、断路器、损失归因
    温度上升 冷却覆盖、供电或容量不足 热力视图、冷却状态、服务降额
    备用设备存在仍中断 路径、电量或接入条件不满足 UPS 缓冲、接线、发电机状态与燃料

    每次比较应记录版本、模式、初始拓扑、流量或需求、改变的变量和观察窗口。随机事件会影响结果；Datacenter Survival 的种子可固定事件内容，但官方架构说明也指出，帧率和起始帧可能造成时序偏差，因此不要承诺两台机器逐毫秒一致。不能把它的种子机制默认套到另一款游戏。

    模拟最适合教因果，不适合替代验收

    两款游戏共同强调的是先定位约束，再选择干预。逻辑层失败需要区分入口、路由、处理和下游；物理层失败需要区分连接、容量、备用路径和热环境。但简化模型省略了大量现实细节，游戏声誉不是正式 SLO，游戏预算不是供应商报价，游戏功率与温度也不是生产容量规划依据。

    源码与测试可说明作者实现和检查了什么，不等于本站独立重跑通过，更不等于模型已覆盖现实。固定版本架构文档甚至说明模拟存在有意保留的单 tick 滞后，提醒读者区分画面反馈、统计更新和物理因果。理解这一点，比把每个数值背成配置口诀更有价值。
