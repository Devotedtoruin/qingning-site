Server Survival 与 Datacenter Survival：请求与机房

2026年9月1日 · 项目 · 约 6 分钟阅读

更新于 2026年9月5日

两款开源浏览器游戏：一个搭云服务架构，一个经营机房供电与散热。附玩法、试玩地址和上手建议。

#开源项目

本页目录

    Server Survival 和 Datacenter Survival 是开发者 Kostyantyn Pshenychnyy（pshenok） 做的两款开源浏览器游戏。一个让你在画布上搭云服务架构，另一个把视角移到服务器背后，管供电、散热和机架。

    两款都能直接在网页里玩，不用注册账号。下面按固定版本的官方说明介绍玩法；在线版本以后可能会变。

    30 秒结论

    想先理解“请求怎么走”选 Server Survival：负载均衡、计算服务、数据库、缓存和队列，最后都落在一条请求路径上。
    想先理解“机房怎么活”选 Datacenter Survival：市电、变压器、UPS、PDU、机架和冷却，任何一环容量不够都会影响下游。



    Server Survival：把请求送对地方

    画布上的节点是负载均衡、计算服务、数据库、缓存和消息队列，移动的小球代表请求。你要买组件、连流向，让合法请求得到处理，同时守住预算、声誉和服务健康度。组件会持续产生维护成本，堆得越多不一定越好。

    游戏分三种模式：

    • Campaign：按关卡目标逐步认识组件，这个版本有 25 关、5 章。
    • Survival：流量不断上涨，还会遇到随机事件，考验架构的余量。
    • Sandbox：可以调预算和流量，没有常规的失败压力。

    每关的起始布局和任务都不一样，不需要先背一套“万能拓扑”。先看当前关卡要求什么，再决定补哪一环。


    前十分钟怎么上手

    先暂停时间，从入口开始连一条最短的路径：负载均衡 → 计算服务 → 数据库。让请求先跑通，再考虑缓存、副本和队列。

    几个组件的作用可以这样理解：

    • CDN：把静态内容放到离用户更近的地方，减少回源。
    • 缓存和只读副本：分担读请求，改变的是负载去向。
    • 队列：把突发流量换成等待，保护后面的服务。
    • Firewall：处理恶意流量，不是所有请求都值得放进来。
    • 扩容和限流：都要看生效时间，临时加机器不一定赶得上流量峰值。



    操作上，左键选择和放置组件，C 切换连线工具，连接有方向；右键拖动画面，滚轮缩放，R 重置视角。建议先暂停，把路径搭好，再用一倍速看请求怎么走。失败标记通常比预算更早告诉你哪里不对。

    Datacenter Survival：让机架活着

    这次的组件是市电、变压器、UPS、PDU、机架和冷却设备。机架有电、温度合适，才能持续带来收入。供电链任何一环容量不够，都可能影响下游负载，严重过载还会触发断路器。


    供电链要看整条，不只看出入口

    市电进来以后，变压器、UPS、PDU 和机架是一条链。只给机架加设备，不扩前面的容量，瓶颈会出现在别处。

    UPS 负责短时接续，备用发电机受启动时间和燃料限制，两者解决的不是同一个时间尺度的问题。先想清楚停电几秒钟、几分钟还是几小时，再决定加什么。

    冷却不是越冷越好

    机架耗电产生热量，冷却设备自己也耗电。除了把温度压下去，还要平衡设备规模、PUE 和费用。T 键可以切换热力图。

    CRAC 适合局部冷却；Chiller 和 CRAH 引入共享冷水系统，规模大时效率更高，但不是越小越划算。先看热力图上的热点，再决定把冷量送到哪里。

    从 The Lab 开始

    这个版本的 Campaign 有 13 关。The Lab 提供一条已经接好的供电链：UPS、备用发电机、三个机架和一个 CRAC，还能手动触发停电、热浪或冷却故障。

    想先认识设备，就从 The Lab 开始；想按目标逐步搭建，再进 Campaign。先观察一条完整链路，比一上来就背设备参数有用。



    两款怎么选

    喜欢画服务拓扑、调请求分流和扩容，选 Server Survival；对供电支路、UPS 接续和机房温度更感兴趣，选 Datacenter Survival。

    两款都有自由观察的模式，不用安装服务端，也不用准备真实云资源。它们适合理解系统之间的因果关系，但不能替代真实的容量规划、电气设计或故障验收。


    想把游戏里的请求路径和机房约束对应到真实系统？可以先读 学习路线 里的 Ubuntu SSH、Hexo/Nginx 和前端文章；游戏适合建立因果直觉，不替代真实容量规划和故障演练。
