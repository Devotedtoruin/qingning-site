Hexo 与 Nginx：构建与安全发布

把 Hexo 生成的静态文件交给 Docker/Nginx：从首次启动到 HTTP 404、目录权限和版本回退。

#Hexo#Docker#Nginx#部署

Hexo 负责把文章和主题生成静态文件，Nginx 负责提供 HTTP 服务。部署时不必把整个 Hexo 项目放进容器：只交付检查过的公开产物，既能缩小公开范围，也让更新和回退更清楚。

下面以一台已安装 Docker Engine 与 Compose 插件的 Linux 服务器为例，演示通过 80 端口提供静态博客。构建端已有可用的 Hexo 项目、符合该项目要求的 Node.js 和按锁文件安装的依赖。域名、DNS 和 HTTPS 证书另行配置；本文的 HTTP 示例不等于已经完成公网 HTTPS 部署。命令是可按环境调整的示例，不是本站服务器的执行记录。

在源码修改内容与配置

在 Hexo 项目中维护文章、主题和站点配置，不直接修改生成的 public/。站点配置里的 url 使用将来对外访问的正式地址，固定链接规则应在首次发布前确定；改完主题后也需要重新生成产物。

默认产物位于 public/。首次发布优先使用干净的构建工作区；旧工作区可能留有已经从源码移除的生成文件，不能仅凭这次生成成功就全部公开。

检查 public/index.html、public/404.html 和实际文章路径，确认样式、图片和脚本都来自这次产物；站点提供搜索、订阅或 sitemap 时，也一并检查。草稿、私有配置、依赖和备份不应出现在文件清单中。开发预览只用于检查页面，不代表公网已经更新。


选择静态文件的交付方式

最简单的交付是把经过审查的 public/ 文件传到服务器的新 release 目录，传输方式可以是 SFTP、rsync 或 CI 产物下载。小站不需要为了运行 Nginx 另外建立产物仓库。

如果需要 Git 记录产物版本，可以使用独立产物仓库。服务器检出目录仍不作为 HTTP 根目录：从选定版本中导出获准公开的文件，再交给 release。只排除 .git/ 并不充分，仓库中的部署脚本、说明文档或托管控制文件也可能不应公开。

try_files 最后的 =404 先产生未找到状态，error_page 再用自定义文件呈现内容，保留 HTTP 404。若把 /404.html 写成普通候选文件，找不到原页面时可能返回 200，浏览器看到了错误页，搜索引擎却认为请求成功。

80:80 将宿主机所有地址的 80 端口映射到容器。先确认端口没有被现有服务占用，再按访问范围配置防火墙和安全组；若已有宿主机反向代理，可改为 127.0.0.1:8080:80，由代理对外提供 HTTPS，不再直接公开这个端口。

验证托管与外部访问

先在服务器检查 HTTP 状态：

首页预期为 200，不存在的页面为 404，点路径被拒绝时通常为 403。再用普通 GET 打开不存在的路径，确认看到自定义错误页，而不是只查响应头。配置中的 internal 表示 /404.html 用于内部错误处理，不是普通文章入口。

随后从服务器外访问公网地址，检查首页、文章、图片、CSS、JS 和错误页。使用域名时核对 DNS 指向；接入 HTTPS 后，再确认有效证书、HTTP 到 HTTPS 的跳转和页面中的资源地址。容器运行、服务器本机请求和外部访问分别检查不同层面，不能相互替代。

同步静态内容与回退

更新时构建并检查新的产物，复制到 releases/v2/，保留 v1。将 Compose 的挂载源从 ./releases/v1 改成 ./releases/v2，检查配置后重建这个服务：

重新执行 HTTP 检查，确认正文与资源属于 v2。失败时把挂载源改回 v1，再执行相同检查和重建步骤。不要只替换宿主机软链接就假定运行中的 bind mount 已转向新目录。

仅修改 nginx.conf 时，先 docker compose exec web nginx -t，成功后 docker compose exec web nginx -s reload。静态文件发布、配置重载和容器重建是不同操作；这个示例的 release 切换不需要重新构建镜像。旧版本保留多久由存储和回退策略决定，不在新版本尚未验收时清理。
