Hexo 与 Nginx：构建与安全发布

2026年9月4日 · 学习笔记 · 约 9 分钟阅读

更新于 2026年9月8日

把 Hexo 生成的 public 交给 Docker/Nginx：目录怎么放、404 怎么写、更新和回退怎么做。

#Hexo#Docker#Nginx#部署

本页目录

    Hexo 的部署其实只有两件事：在本地把文章生成静态文件，再让 Nginx 指向这些文件。真正容易出问题的，是目录权限、404 状态码和版本回退这些细节。

    一个常见的误区是把整个 Hexo 项目扔进容器。容器只需要公开的 public/，源码、依赖、.git 和备份都不应该出现在网站根目录里。把交付物缩小到“已检查的静态文件”，更新和回退都会简单很多。

    下面以一台已经安装 Docker Engine 和 Compose 插件的 Linux 服务器为例，通过 80 端口提供 HTTP 服务。域名、DNS 和 HTTPS 证书另行配置；文中的 HTTP 示例不等于已经完成公网 HTTPS 部署。

    学习路线 · 02 这篇属于“从服务器到前端”的学习路线。查看完整路线 →


    先定目录结构

    用发布账号自己的目录，不要先用 root 建目录，再让普通用户往里复制。一个够用的结构如下：

    Nginx 每次只挂载一个 release。源码、依赖、备份和 .git 都放在这个目录之外；用不用 Git 交付，都不影响这条边界。

    如果服务器规范要求把站点放在 /srv，让管理员提前建好目录、设置属主，并检查每一级父目录的遍历权限。目录权限不对，Nginx 容器再正确也会返回 403。


    在源码里改，不碰生成目录

    文章、主题和站点配置都在 Hexo 项目里维护。不要直接改 public/，下次生成会被覆盖。

    站点配置里的 url 填将来对外访问的正式地址，固定链接规则最好在第一次发布前定下来。改了主题或配置后，记得重新生成产物。

    自定义 404 也应该有源文件。如果项目里还没有错误页，可以在 source/404.html 放一个最小页面；主题已经提供 404 的话，直接用主题的，不要额外覆盖。

    这里假设站点部署在域名根路径。如果部署在子目录，页面链接、资源路径和 Hexo 的 root 配置要一起调整。

    在 Hexo 项目根目录运行：

    默认产物在 public/。首次发布最好从干净的构建开始；旧工作区可能残留已经从源码删掉的页面，不能因为这次生成成功就全部公开。

    生成后至少检查这几项：

    • public/index.html、public/404.html 和实际文章路径能打开。
    • 样式、图片和脚本来自这次产物，不是旧缓存。
    • 草稿、私有配置、依赖和备份没有混进文件清单。
    • 搜索、订阅或 sitemap 如果启用了，也一起检查。

    本地预览只用于看页面，不代表公网已经更新。


    把文件送到服务器

    最简单的办法是把检查过的 public/ 传到服务器的新 release 目录，SFTP、rsync 或 CI 产物下载都可以。小站不需要为了跑 Nginx 专门建一个产物仓库。

    如果希望用 Git 记录每次发布，可以建一个独立的产物仓库。注意：服务器上的检出目录仍然不要直接当网站根目录。从选定版本里导出允许公开的文件，再交给 release。只排除 .git/ 还不够，仓库里的部署脚本、说明文档和托管平台配置文件也可能不应该公开。

    容器里的 Nginx 工作进程需要读取文件、遍历目录。这里让公开文件可读、目录可遍历，但不给其他账号写权限。不要用 chmod -R 777。:ro 只限制容器写挂载内容，不会自动修好宿主机上的读取权限。

    复制失败就先查原因，不要继续启动容器。重新复制时另选一个新版本目录，不要把半成品当成完整版本。

    在 ~/static-blog/nginx.conf 保存下面的配置。它只提供静态文件，不启用目录列表，也不把所有未知路径改写成首页：

    try_files 最后的 =404 先产生“未找到”状态，error_page 再用自定义文件呈现内容，HTTP 状态仍然是 404。如果把 /404.html 写成普通候选文件，找不到页面时可能返回 200：浏览器看到的是错误页，搜索引擎却以为请求成功。

    点路径拒绝规则只是一道额外防线，不能代替公开文件审核。需要 HTTP-01 证书验证时，要另外给 /.well-known/acme-challenge/ 留受限例外。

    再在同一个目录保存 compose.yaml：

    nginx:1.28.0-alpine 只是固定版本的示例，不代表它是当前最新版或长期受支持的版本。实际部署时选经过评估的受支持版本，按需要记录镜像 digest；后续更新也要明确版本，不要用浮动的 latest 代替更新计划。

    80:80 会把宿主机所有地址的 80 端口映射到容器。先确认端口没有被现有服务占用，再按访问范围配置防火墙和安全组。如果宿主机已经有反向代理，可以改成 127.0.0.1:8080:80，由代理对外提供 HTTPS。

    然后从服务器外访问公网地址，检查首页、文章、图片、CSS、JS 和错误页。使用域名时核对 DNS；接入 HTTPS 后，再确认证书、HTTP 到 HTTPS 的跳转和页面里的资源地址。容器状态、本机请求和外部访问检查的是不同层面，不能互相替代。

    常见问题

    现象 先查什么
    403 Forbidden release 目录和文件权限、每一级父目录的遍历权限、SELinux/AppArmor
    404 但文件存在 root 路径、挂载路径、try_files、文件名大小写
    502 Bad Gateway 这个示例里通常不是 Nginx 本身，检查是否有上层反向代理指向了错误端口
    address already in use 宿主机 80 端口占用，ss -ltnp 查到进程后再决定怎么处理
    改了配置没生效 是否执行了 nginx -t 和 reload；容器是否重建
