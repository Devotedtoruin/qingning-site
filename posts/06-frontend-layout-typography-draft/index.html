    静态博客前端（一）：从页面骨架到可阅读的布局排版

    以本站 Hexo 主题为例，梳理模板职责、Grid 收缩、阅读宽度、目录顺序与代码表格的溢出处理。

    #Hexo#CSS#响应式设计#排版

    博客的布局不是把截图里几个矩形排齐，而是让标题、正文、目录和工具在内容变化后仍有清晰关系。短标题、没有封面的卡片、长代码与手机放大阅读，都应成为设计输入，而不是最后才发现的例外。

    本文依据本站 ops-journal 主题源码讲解，不把独立视觉稿当成实际页面，也没有在本次起草中完成浏览器验收。文中的独立代码示例用于解释布局，不是整份主题的替代实现；源码核对不等于完成浏览器视觉验收。本系列后两篇分别讨论分层背景，以及 PJAX 与持续播放器的生命周期。

    先分清模板负责什么

    主题的 layout/index.ejs 负责首页正文列表和侧栏，layout/post.ejs 负责文章骨架；共用页头、页脚由 _partial/header.ejs 与 _partial/footer.ejs 输出。最外层 layout/layout.ejs 承担 body 外壳，并不是另一个重复包裹所有页头的容器。

    首页模板目前把最新文章放在主体列，再调用首页侧栏 partial。文章页则包含目录导航、文章头、.article-content 和文末返回入口。Markdown 的 h2/h3 是正文结构，页面 h1 是文章标题；不能为视觉字号把一个次级小节提升为 h2，也不应为了目录漂亮给每段都加标题。

    这套职责划分使修改范围可以预测：卡片样式影响列表，文章正文样式影响阅读页，页头影响所有页面。排版调整应先找到对应容器，而不是通过一串全局 div 选择器改变所有区域。

    Grid 最容易忽略的是能否收缩

    首页采用正文与轻侧栏，文章页宽屏采用目录与正文的双列。列宽要容纳内容，但也必须允许长内容在本列内处理。以下是同类布局的简化示例，不是待直接覆盖主题的完整补丁：

    1fr 并不总能解决长内容问题。网格项目默认的最小尺寸可能受到长单词、代码或图片影响；minmax(0, 1fr) 与子项目的 min-width: 0 允许列收缩，再由代码块或表格承担必要的横向滚动。把整页 overflow-x: hidden 当作修复，只是把内容裁掉，键盘用户仍可能无法读完。

    本站 CSS 中 .content-main、.article-main、.post-summary 均有收缩或换行约束。文章卡片还有有封面与无封面两种布局，小屏将封面移到独立一行。这意味着测试不能只看一张封面卡片：至少要覆盖空摘要、长标题、多标签以及没有图片的卡片。

    限制阅读宽度，而不是无限填满屏幕

    大屏上能显示更多字，不代表应该把正文扩展到窗口边缘。行太长会增加换行后寻找下一行起点的成本；行太短又让长代码频繁溢出。中文、英文和技术符号混排时，不能机械套用单一字符数。

    主题用 shell 控制外边距，用文章布局分配目录与正文，再给正文面板留内边距。正文宽度并不等于 shell 宽度：目录列、列间距、边框与面板 padding 都会消耗可用空间。排查“文章看起来很窄”时应看计算后的盒模型，而不是只把外层 max-width 加大。

    字体也有职责差异。本站标题使用本地托管的 Noto Serif SC 字重资源，正文优先系统无衬线，代码使用等宽字体。标题字体加载失败时应落到回退字体，而不是让正文不可见。对长中文标题，要检查换行、字距和字体替换后的高度变化，不能只凭字体成功加载一次就认定稳定。

    目录的位置和阅读顺序要一起设计

    post.ejs 的目录导航在 DOM 中位于 article 前面，脚本从正文 h2/h3 构建父子列表。CSS 可以通过 order 改变视觉位置，但不会自动改变读屏器和 Tab 的遍历顺序。因此左侧还是右侧目录不是纯审美问题，还应检查键盘用户是否先经过过长目录才能进入正文，以及窄屏折叠是否可操作。

    当前源码使用 sticky 目录和折叠按钮；目录高度受视口约束并可滚动。sticky 的 top、标题的滚动落点和页头高度需要一起验收。若页头在手机上多一行，沿用大屏的固定偏移可能让章节标题被遮挡。

    本站目录在宽屏位于左侧，900 px 起采用双列，窄屏默认折叠。维护时应确认：视觉位置与文案一致；按钮的 aria-expanded、实际列表可见状态同步；正文标题的锚点有效；在底部短小节也能得到正确高亮。

    普通表格与代码高亮表格不能共用一套规则

    Hexo 高亮输出可能包含 figure.highlight 内的 table，它不是业务数据表格。普通表格要考虑列标题、换行和阅读关系；代码要保持空格与缩进，并在块内滚动。对所有 .article-content table 都设置相同的 hover 底色和 cell padding，可能破坏代码宽度与对齐。

    本站 CSS 单独定义高亮 figure、table、td 和 pre；site.js 包装普通表格时跳过高亮 figure 与已包装表格。语言标签、复制按钮又由脚本添加，所以首次打开正常不够，还要检查 PJAX 进入文章后是否仍只有一个按钮。

    溢出检查应使用具有意义的长内容：长 URL、长中文单元格、连续代码字符与多列数据。数据表不能为了适配手机把列之间的对应关系拆散；确需横向滚动时，滚动容器应有名称且可由键盘访问。复制代码不应连同语言标签、行号或按钮文案一起复制。

    阅读时间和邻文在构建时计算

    文章头与列表卡片的“约 N 分钟阅读（粗估）”来自 scripts/reading.js，不是访客统计。它先从正文 HTML 提取纯文本，按中文字符数除以 300、其余字母数字词数除以 200 相加，向上取整，至少 1 分钟。代码和技术符号也会影响估计，图片与推理难度并不会被充分表达，不能把粗估当成读者必须完成的倒计时。

    文末上一篇、下一篇也在构建时选择：先按公开条件过滤，再按日期升序排列；上一篇较早，下一篇较新，同日期按路径排序。没有邻文的一端不生成假链接。邻文不是直接信任 Hexo 的原始 prev/next，因此未发表的运维草稿不会因为排在中间而被推荐。

    排查异常时，先查文章 date、draft 与 published，再查 helper 和生成 HTML。改日期会改变顺序，但不等于文章过去已经公开；阅读时间发生变化也不代表测到了访客读得更快。

    浮动工具应避开页脚，而不是挤大正文

    播放器与返回顶部固定在视口边缘。主题用 --floating-lift 把它们在页脚进入视口时抬高：site.js 测量正常文档流中 .site-footer 与视口的重叠高度，向上取整后写入变量，CSS 的 bottom 再加安全区和原有间距。测量对象不是已经被抬高的按钮，否则容易形成自我反馈。

    滚动与 resize 通过 requestAnimationFrame 合并测量，PJAX 的每页 mount 也会安排更新。这个变量只服务浮动底部位置，不应加到卡片、标题或目录内部间距上。检查应走到短页和长文末尾，确认按钮不遮页脚链接、播放器展开不挡关键控件；源码公式不能代替触屏与键盘验收。

    用验收场景代替“看起来差不多”

    可以按以下顺序审查实际生成页面，而不是在生产站点直接试改：

    1. 在窄屏检查页头工具、标题和卡片，确认整页没有横向滚动。
    2. 放大文字或页面，检查双列能否转为单列，按钮是否仍可见。
    3. 用键盘经过目录、复制按钮、表格与返回入口，确认焦点不被固定播放器遮挡。
    4. 检查长代码只在块内滚动，正文与代码块左右边界一致。
    5. 检查无 JavaScript 时仍可阅读正文、访问文章链接和原图。
    6. 用真实的生成页面复核字体、目录锚点与页面底部，不把示意图作为验收证据。

    本文只将源码可确认的结构与操作列为实现事实，没有生成上述浏览器结果。CSS 存在多段历史覆盖规则，最终表现以级联和媒体条件的计算结果为准；后续整理不能仅删掉看似重复的选择器而不比较页面。
