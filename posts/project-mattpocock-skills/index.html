mattpocock/skills：Matt Pocock 公开的工程 Skill 集

2026年9月12日 · 项目 · 约 5 分钟阅读

更新于 2026年9月16日

Matt Pocock 公开的工程 Skill 集，把需求、架构、调试、测试和审查写成 Agent 可执行的流程。

#AI#开源项目#Agent

本页目录

    mattpocock/skills 是 Matt Pocock 从自己日常 .agents 目录公开的工程 Skill 集，主页在 aihero.dev/skills。它不替模型补代码，而是把资深工程师的默认动作拆成可调用流程：需求不清先追问，改代码前看架构，完成后跑测试和审查。README 的定位是“给真正的工程用”，并明确反对把整个开发过程交给一套重型方法论。按官方 README 整理，未在本机完整实测。

    两类 Skill：你点名的和模型自己取的

    仓库把 Skill 分成两轴。用户调用型只有在你输入命令时才触发，职责是编排流程，例如 /grill-me、/to-spec、/implement。模型调用型既可以由你点名，也可以在任务合适时被 agent 自动取用，承载可复用的纪律，例如 /tdd、/diagnosing-bugs、/code-review。用户调用型可以调用模型调用型，但不能调用另一个用户调用型，避免流程套流程、最后没人知道执行到哪一步。

    从追问到审查的一条链

    需求阶段，/grill-me 会持续追问，直到设计树的每个分支都有答案；/grill-with-docs 在此基础上同步整理领域术语，更新 GLOSSARY.md 和 ADR。规格阶段，/to-spec 把当前对话整理成规格并发布到 issue tracker，/to-tickets 再拆成带阻塞关系的 tracer-bullet 工单。

    实现阶段，/implement 按工单推进，在事先约定的接缝上调用 /tdd，提交前跑 /code-review。/code-review 分两条轴并行：Standards 看代码是否符合仓库规范，并用 Fowler 的坏味道清单做基线；Spec 看改动是否忠实实现了原工单。两条轴由不同子 agent 执行，避免互相污染。

    遇到难查的 bug，/diagnosing-bugs 要求先建立“能在这个 bug 上变红”的反馈回路，再最小化、提假设、加观测、修复、补回归测试。/improve-codebase-architecture 扫描代码库里可以“加深”的模块，输出 HTML 报告，再和你逐个讨论候选。README 特意说明它是调查，不是抢救：老代码库能找出真实候选，但不会替你拆解泥球。

    一个返工场景

    接手一个老仓库，需求只有一句“把结算流程改快一点”。直接让 agent 改，通常会在错误的地方做优化。更合适的顺序是：/grill-with-docs 把结算的领域词和边界问清楚，顺手补词汇表；/to-spec 固化成规格；/to-tickets 拆出可独立验证的工单；/implement 逐张推进；最后 /code-review 检查规范和规格两条轴。流程不会让代码自动变好，但能减少“做完才发现做错方向”的返工。每步都留下产物：词汇表、规格、工单、测试和审查记录，换会话或换人时不用从头解释。

    只改一行拼写错误时，这套流程明显过重，直接改更快。

    与 GSD、BMAD、Spec-Kit 的取舍

    README 的对比是：GSD、BMAD、Spec-Kit 这类方法试图接管整个流程，代价是控制权转移，流程本身出问题时也不容易修。这些 Skill 选择另一条路：保持小而可改、可组合，不绑定模型，由使用者自己拼装。代价是你要判断当前该用哪一条，仓库不会替你做主；对不熟悉工程流程的人，选项本身也可能成为负担。

    流程的代价

    一次性配置和每个仓库的 setup 都要花时间；Skill 会让对话变长，简单任务显得啰嗦。用户调用型依赖各工具对命令/插件的支持程度，模型调用型的触发则取决于 harness，换一个 agent 行为可能不同。Skill 也不能替代类型检查、测试、浏览器访问和人工 review；README 把反馈回路视为代码质量的前提，而不是 Skill 的附属品。

    项目入口

    • 仓库：mattpocock/skills
    • 主页：aihero.dev/skills
    • 许可：MIT
    • 适合：已经在用 Claude Code、Codex 等 coding agent，希望把需求澄清、TDD、调试和审查变成固定动作的工程师
