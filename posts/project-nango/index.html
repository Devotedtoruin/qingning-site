Nango：开源 API 集成平台

2026年9月2日 · 项目 · 约 5 分钟阅读

更新于 2026年9月6日

开源 API 集成平台，连接 1000+ API。

#开源项目#效率工具

本页目录

    Nango 是一个开源的 API 集成平台，目标是让产品或 AI Agent 用一套统一的方式连接 1000 多个外部 API。它由 NangoHQ 维护，TypeScript 编写，2020 年创建，官网 nango.dev。核心工作是把 OAuth、凭据刷新、多租户连接、请求代理和集成函数收进一个运行时，开发者只写业务逻辑，不用为每个 SaaS 重做一遍授权和 token 管理。本文按官方 README 整理，未在本机完整实测；API 覆盖和许可条款以官方文档为准。

    三个原语：Auth、Proxy、Functions

    README 把能力归纳为三块。

    Auth：托管 OAuth、API Key 和 token 刷新，覆盖 1000 多个 API。前端可以嵌入白标授权流程：

    凭据存储、多租户连接和刷新由 Nango 负责，产品侧只需保存 connectionId。

    Proxy：替用户发起带授权的请求。它解析 provider、注入凭据、处理重试和限流，然后返回响应：

    Functions：把集成逻辑写成 TypeScript 函数，部署到 Nango 的运行时，自带 API 访问、重试、存储和可观测性。函数可以手写，也可以让 AI builder 根据描述生成。README 强调生成的是可读、可审查、可版本控制的代码，而不是黑盒配置；官方还提供类型检查和测试框架。

    面向 Agent 的工具调用

    README 把“AI tool calling & MCP”列在用例第一位：给 Agent 调用外部 API 的能力，认证和限流交给 Nango。除此之外还覆盖数据同步（为 RAG 建索引、做单向或双向同步）、Webhook 处理、API 统一（把多个服务归一成自己的 schema）、写操作 Actions，以及按客户定制集成行为。

    对做 Agent 产品的团队，这解决了一个很实际的问题：模型会调用工具，但工具背后的 OAuth 授权、token 过期和多租户隔离不该由提示词处理。Nango 把这些放到平台层，Agent 只看到“已连接的账号”。平台可以通过 CLI 和 API 操作，兼容任意后端语言，也兼容 Cursor、Codex、Claude Code 等编码工具以及 MCP、LangChain 等 Agent SDK。

    部署与许可

    README 给出三种运行方式：Nango Cloud、BYOC（部署到自己的云账号）和免费自托管。Cloud 与 BYOC 按套餐提供全部功能，免费自托管功能受限。自托管适合数据不能出内网的团队，但要自己维护数据库、运行时和密钥管理；BYOC 把运行环境放在自己的云账号里，运维责任仍由自己承担一部分。

    许可证是 Elastic License，不是 MIT 或 Apache。商用、分发和托管服务前要读仓库 LICENSE 和定价页，确认自己的使用方式是否被允许。

    典型场景

    一个 SaaS 产品想支持“连接你的 GitHub 和 Slack”：用户在设置页点授权，Nango 弹出白标 OAuth 流程，完成后产品拿到 connectionId。后端通过 Proxy 读取仓库列表、发消息，不需要自己实现 OAuth 回调、刷新 token 和处理每个租户的凭据。之后再加一个 CRM，只写一个同步函数，不用改认证框架。对 Agent 产品，同一套连接可以直接暴露成工具，让模型替用户执行操作。

    和自己写 OAuth、iPaaS 的差别

    自己接 API 意味着每个服务都要处理授权流程、token 刷新、限流、重试和错误映射，接五个服务就会长出五套相似代码。Zapier、Make 这类 iPaaS 面向无代码自动化，适合把现成应用串起来，但不容易嵌进产品自己的界面和权限模型。Nango 的位置在两者之间：代码可控，认证和运行时托管，前端还能嵌入授权 UI。

    限制与风险

    1000 多个 API 是官方目录的数量，具体某个服务的覆盖深度、字段和权限仍要看文档；冷门 API 可能要自己写函数。自托管免费版功能有限，生产环境用 Cloud 或 BYOC 会产生费用。凭据集中在 Nango 后，密钥管理、租户隔离、审计和备份都成为关键风险，部署前要明确谁能访问 secret key。平台版本和 API 行为会变化，升级与迁移也要预留时间。

    适合谁

    适合要把多个 SaaS 接进自己产品、又不愿为每个服务重写 OAuth 的工程团队；也适合给 Agent 提供外部工具调用的平台开发者。只需要接一两个 API、且没有多租户需求的内部脚本，直接写 HTTP 客户端更轻。

    入口

    • 官网：nango.dev
    • 文档：nango.dev/docs
    • API 目录：nango.dev/docs/integrations/overview
    • 许可证：Elastic License（以仓库 LICENSE 为准）
